# 本地内容系统控制台设计 Spec

日期: 2026-06-11

状态: 设计稿。用于后续实现前的工程依据。

## 1. 背景

本项目已经形成一套本地优先的 AI 内容生产系统:

- 后端能力集中在 `backend/app`，主要通过 `python3 -m app.cli.main ...` 暴露。
- 内容资产沉淀在 `content-vault/`，以 Markdown 和附件目录为事实来源。
- 日常素材准备由 macOS `launchd` 定时执行 `daily-pipeline`。
- 运行证据写入 `data/runs/YYYY-MM-DD.jsonl`。
- 分析任务包写入 `data/processed/analysis-packs/`。
- Codex 负责读取任务包、prompt 和 Markdown 产物，完成分析、选题、写作判断。

当前问题不是能力缺失，而是能力入口分散:

- 用户不容易一眼知道系统今天是否正常。
- 用户不容易知道下一步应该让 Codex 做什么。
- 失败原因散落在运行日志里。
- 单链接入库、手动同步、媒体处理、任务包生成等动作都需要记命令。
- 跨会话使用时，新的 Codex 需要重新读文档才能判断系统状态。

因此需要一个轻量本地控制台，把现有 CLI、文件和日志变成可视化入口。

## 2. 目标

第一版控制台解决四件事:

1. 让用户知道系统有什么能力。
2. 让用户知道今天素材准备是否正常。
3. 让用户知道当前流程卡在哪一步，以及下一步该让 Codex 做什么。
4. 让用户能安全触发少量固定动作。

第一版不追求成为完整内容管理系统。

## 3. 非目标

第一版不做:

- 数据库。
- 队列系统。
- 多用户登录。
- 内容富文本编辑器。
- 自动发布。
- 平台表现数据自动采集。
- 在前台里直接完成 AI 分析和写作。
- 替代用户与 Codex 的对话。
- 对 `.env.local`、密钥、登录配置做可视化展示。

前台只做状态、入口、导航和安全触发。AI 判断仍由 Codex 在对话里完成。

## 4. 推荐方案

采用轻量本地 Web 控制台:

```text
本地控制台 UI
  -> 本地 HTTP API
  -> 现有 backend service / CLI 能力
  -> content-vault Markdown
  -> data/runs 运行日志
  -> data/processed 分析任务包
  -> launchd 定时状态
```

约束:

- 默认只监听 `127.0.0.1`。
- 默认不接外网。
- 不引入数据库。
- 不允许执行任意命令。
- 所有可触发动作必须来自白名单能力注册表。

## 5. 架构

建议新增:

```text
backend/app/web/
  __init__.py
  server.py          本地 HTTP 服务入口
  dashboard.py       汇总状态、运行记录、产物导航
  capabilities.py    能力注册表
  actions.py         白名单动作执行层
  schemas.py         返回结构和状态口径
  static/            简单 CSS/JS
  templates/         页面模板
```

第一版可以用 Python 标准库或轻量依赖实现。若引入新依赖，需要优先考虑可维护性和本地安装成本。

### 5.1 数据流

```text
页面加载
  -> GET /api/overview
  -> dashboard.py 读取 status、runs、analysis-packs、content-vault
  -> 返回今日总览、失败摘要、下一步建议、最近产物

用户触发动作
  -> POST /api/actions/<action_id>
  -> actions.py 校验 action_id、参数、运行锁
  -> 调用现有 service 或 CLI
  -> 写入 data/runs / 生成产物
  -> 返回结构化结果
```

## 6. 能力注册表

必须有一张固定能力清单，前台页面和动作层都从这里读取。

每个能力包含:

```text
能力 ID
显示名称
说明
类型: 只读 / 写入 / 长任务
风险等级: low / medium / high
是否默认启用
对应入口: service 函数或 CLI 参数
需要参数
产物位置
最近一次运行状态
失败时建议
```

第一版能力:

| 能力 ID | 名称 | 类型 | 风险 | 说明 |
| --- | --- | --- | --- | --- |
| status.overview | 今日总览 | 只读 | low | 读取目录、素材数、运行日志、产物 |
| ingest.url | 单链接入库 | 写入 | medium | 支持抖音、小红书、公众号链接 |
| run.daily_pipeline | 手动跑日常流程 | 长任务 | medium | 执行素材准备、媒体处理、任务包生成 |
| sync.douyin | 同步抖音 ai 收藏夹 | 长任务 | medium | 单独触发抖音固定来源 |
| sync.wechat | 同步公众号文章 | 长任务 | medium | 单独触发公众号固定来源 |
| sync.aihot | 同步 AI HOT | 长任务 | low | 同步外部 AI 热点 |
| process.media | 媒体转可读内容 | 长任务 | medium | 处理本地附件 |
| build.packs | 生成分析任务包 | 写入 | low | 生成每日、滚动、候选任务包 |
| open.outputs | 产物导航 | 只读 | low | 打开素材、任务包、分析卡、内容生产文件 |

小红书能力保留，但第一版默认显示为“已关闭 / 可手动启用”，不放在首页主操作里。

## 7. 今日状态口径

首页必须区分以下状态:

```text
未运行: 今天没有 data/runs/YYYY-MM-DD.jsonl
运行成功: 今天最近一次 daily-pipeline 没有失败步骤
部分成功: 今天最近一次 daily-pipeline 有失败步骤，但任务包或部分素材仍生成
运行失败: 核心步骤失败且没有可用产物
无新增: 步骤成功，但新增素材为 0 或全部重复
等待 AI 分析: 任务包已生成，但每日分析卡未生成
等待选题: 每日分析卡存在，但候选池未更新或未选择题
等待写作: 已有候选题，但没有内容生产文件
等待发布/复盘: 已有内容生产文件或发布记录，但复盘未补
```

不得把“无新增”显示成失败。

不得把“部分成功”隐藏成成功。

## 8. 首页设计

第一版首页分五块。

### 8.1 今日总览

展示:

- 今日日期。
- 最近一次日常流程运行时间。
- 总状态: 成功 / 部分成功 / 失败 / 未运行。
- 今日新增素材数量。
- 今日重复素材数量。
- 今日失败步骤数量。
- 今日任务包是否生成。
- 今日分析卡是否存在。
- 今日候选池是否存在。

### 8.2 下一步建议

根据状态生成一个主建议，最多两个备用建议。

示例:

```text
素材和任务包已准备好，可以让 Codex 写每日素材分析卡。
公众号同步失败，但 AI HOT 和任务包已生成，可以先基于现有素材分析。
今天没有新增素材，可以查看近 7 日滚动分析或手动入库一个链接。
```

每条建议附带可复制提示词，例如:

```text
请读取 AGENTS.md、三个固定 prompt，以及 data/processed/analysis-packs/2026-06-11-daily-material-analysis.md，写今天的每日素材分析卡。
```

### 8.3 失败摘要

只显示可读摘要，不输出敏感配置。

展示:

- 失败步骤。
- 失败时间。
- 错误类型摘要。
- 完整日志路径。
- 建议动作。

错误示例:

```text
sync-wechat-mp-articles: 本地公众号服务鉴权失败。建议检查 we-mp-rss 登录/配置。
sync-douyin-collections: 请求超时。建议稍后重试或单独触发抖音同步。
```

### 8.4 能力快捷入口

第一版只放:

- 单链接入库。
- 手动跑日常流程。
- 生成分析任务包。
- 媒体处理。

其他能力放到“能力中心”页。

### 8.5 最近产物

展示:

- 最新素材卡。
- 最新可读内容。
- 今日分析任务包。
- 今日滚动任务包。
- 今日候选任务包。
- 今日每日分析卡。
- 今日候选池。
- 最近内容生产文件。

每个产物显示:

- 文件名。
- 类型。
- 更新时间。
- 相对路径。
- 打开方式。

## 9. 页面信息架构

第一版页面:

```text
/                 首页总览
/capabilities     能力中心
/runs             运行记录
/materials        素材与产物
/health           系统健康
```

### 9.1 能力中心

显示能力注册表。

每个能力显示:

- 能力名称。
- 说明。
- 当前是否启用。
- 最近一次执行状态。
- 关联命令说明。
- 主要产物位置。
- 可触发按钮。

写入类动作需要确认。

长任务需要运行中状态和锁。

### 9.2 运行记录

读取 `data/runs/YYYY-MM-DD.jsonl`。

展示:

- 日期选择。
- 每次 `daily-pipeline` 的 run_id。
- 步骤时间线。
- ok / skipped / failed 状态。
- 失败摘要。
- 产物路径。

解析规则:

- 以 `run_id` 聚合。
- `daily-pipeline` 总结行作为一次运行的结论。
- 步骤行作为明细。
- 如果没有总结行，则按最后一条相关步骤推断为“不完整记录”。

### 9.3 素材与产物

按流程展示:

```text
素材卡
  -> 可读内容
  -> 每日任务包
  -> 每日分析卡
  -> 滚动分析卡
  -> 候选池
  -> 内容生产文件
  -> 发布记录
  -> 复盘
```

第一版只做最近列表和路径导航，不做全文搜索。

### 9.4 系统健康

展示:

- `launchd` 任务是否存在。
- 最近一次自动运行时间。
- 项目目录是否完整。
- `data/runs` 是否可写。
- `content-vault` 是否存在。
- `we-mp-rss` 本地服务是否可达。
- 小红书是否关闭。
- 抖音配置是否存在但不显示内容。
- AI HOT 是否启用。

健康检查不输出 `.env.local` 内容。

## 10. API 设计

第一版 API:

```text
GET  /api/overview
GET  /api/capabilities
GET  /api/runs?date=YYYY-MM-DD
GET  /api/artifacts?date=YYYY-MM-DD
GET  /api/health
POST /api/actions/ingest-url
POST /api/actions/run-daily-pipeline
POST /api/actions/sync-source
POST /api/actions/process-media
POST /api/actions/build-packs
```

返回:

```json
{
  "date": "2026-06-11",
  "status": "partial",
  "latest_run": {
    "run_id": "31cdd8970c31",
    "created_at": "2026-06-10T18:31:05+08:00",

  "counts": {
    "materials_total": 322,

  "artifacts": {
    "daily_pack": "...",
    "rolling_pack": "...",
    "topic_pack": "...",
    "daily_analysis": "",
    "topic_candidates": ""
  },
  "next_actions": []
}
```

字段可以扩展，但第一版必须保持稳定。

### 10.2 `POST /api/actions/ingest-url`

请求:

```json
{
  "url": "https://...",
  "download_media": true,
  "download_images": true,
  "media_limit": null,
  "image_limit": 20
}
```

返回:

```json
{
  "ok": true,
  "message": "已入库",
  "material_path": "...",
  "attachment_paths": []
}
```

### 10.3 `POST /api/actions/run-daily-pipeline`

第一版不提供任意参数编辑，只允许:

```json
{
  "date": "",
  "force": false
}
```

后续再开放数量、来源和媒体限制。

## 11. 操作安全

所有写入类和长任务动作必须经过 `actions.py` 白名单。

要求:

- 禁止接受任意 shell 字符串。
- 禁止前台传入完整命令。
- 禁止展示密钥和登录配置。
- 同一时间只允许一个长任务运行。
- 长任务运行中，相关按钮置灰。
- 运行结果必须写入可追踪日志。
- 失败时展示摘要和日志路径。
- 对可能耗时或写入大量文件的动作做确认。

运行锁:

```text
data/runtime/web-action.lock
```

锁内容:

```json
{
  "action_id": "run.daily_pipeline",
  "started_at": "2026-06-11T10:00:00+08:00",
  "pid": 12345
}
```

如果锁超过 2 小时，显示“疑似残留锁”，需要用户确认后清理。

## 12. 错误处理

错误展示分三级:

```text
用户可读摘要: 首页和运行记录展示
技术详情: 折叠展示，不包含敏感配置
完整证据: 日志文件路径
```

常见错误映射:

| 错误特征 | 用户摘要 | 建议动作 |
| --- | --- | --- |
| HTTP 401 | 本地服务鉴权失败 | 检查对应服务登录/配置 |
| timeout | 请求超时 | 稍后重试或单独触发该来源 |
| Operation not permitted | 当前执行环境无法访问本机端口或代理 | 用 macOS 定时任务或本地服务执行 |
| SSL EOF | 网络连接被中断 | 检查代理/网络后重试 |
| no new items | 没有新增素材 | 不是失败，可继续滚动分析 |

## 13. 文件打开策略

本地控制台不直接编辑 Markdown。

第一版提供:

- 复制路径。
- 在浏览器打开 HTML。
- 显示 Markdown 文件相对路径。

后续可考虑:

- 调用系统打开 Obsidian。
- 调用 `open` 打开 Finder。

这些后续动作需要安全确认。

## 14. UI 风格

控制台应该是工作型界面，不做营销风。

视觉原则:

- 信息密度适中。
- 清晰状态色。
- 少装饰。
- 首页优先展示“今天能不能继续推进”。
- 操作按钮少而明确。
- 失败信息不要吓人，但要可定位。

建议布局:

```text
顶部: 项目名 / 今日状态 / 最近运行时间
左侧: 首页、能力中心、运行记录、素材产物、系统健康
主区: 状态卡 + 下一步建议 + 失败摘要 + 最近产物
```

## 15. 开发顺序

### 阶段 1: 只读总览

实现:

- 本地服务启动。
- 首页总览。
- 运行记录读取。
- 产物导航。
- 系统健康只读。

不实现:

- 写入类动作。
- 运行按钮。

验收:

- 能看到今日最近一次运行状态。
- 能看到失败步骤。
- 能看到任务包路径。
- 能区分失败、部分成功、无新增。

### 阶段 2: 安全操作入口

实现:

- 单链接入库。
- 手动跑日常流程。
- 生成任务包。
- 媒体处理。
- 运行锁。
- 动作结果摘要。

验收:

- 不能传任意命令。
- 连点按钮不会并发跑长任务。
- 成功/失败都能在运行记录里追踪。

### 阶段 3: Codex 协作入口

实现:

- 根据当前状态生成 Codex 提示词。
- 一键复制“写每日分析卡”提示。
- 一键复制“基于候选池选题”提示。
- 一键复制“进入写作流程”提示。

验收:

- 新会话可以靠提示词和固定路径继续流程。
- 不需要用户手动记任务包路径。

### 阶段 4: 发布与复盘辅助

实现:

- 发布记录入口。
- 复盘模板入口。
- 待复盘提醒。

暂不自动采集平台表现数据。

## 16. 测试计划

后端测试:

- 能力注册表返回稳定结构。
- runs 解析能聚合 run_id。
- overview 能正确识别 ok / partial / failed / no-run / no-new。
- actions 拒绝未知 action_id。
- 写入类动作会创建/释放锁。
- 错误摘要不会包含 `.env.local` 内容。

人工验证:

- 打开首页能看懂今天状态。
- 最近一次失败能定位到日志。
- 单链接入库能生成素材卡。
- 手动日常流程不会并发执行。
- 任务包路径能被复制给 Codex。

## 17. 验收标准

第一版完成后，用户应该能回答:

1. 今天系统有没有跑。
2. 哪些来源成功，哪些失败。
3. 今天有没有新增素材。
4. 任务包是否已经生成。
5. 下一步应该让 Codex 做什么。
6. 如果失败，应该先看哪里。
7. 如果临时看到一个链接，应该从哪里入库。

如果以上问题还需要回终端查命令，第一版就没有达到目标。

## 18. 后续可能升级

发布 1-5 篇后:

- 增加发布记录录入入口。
- 增加待复盘提醒。

发布 5-10 篇后:

- 增加轻量表现数据输入。
- 增加预测与实际对比看板。

发布 10 篇以上后:

- 再考虑更复杂的复盘评分、选题表现趋势和系统自我升级看板。

## 19. 待用户确认

实现前需要确认:

1. 第一版是否只做本地网页，不做桌面 app。
2. 是否接受第一版先不做 React，用简单模板快速落地。
3. 手动操作第一版是否只开放单链接入库、日常流程、媒体处理、任务包生成。
4. 是否需要在首页显示小红书“已关闭”状态，还是先完全隐藏。
