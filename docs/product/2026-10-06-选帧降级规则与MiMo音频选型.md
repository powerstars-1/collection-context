# 选帧降级规则与 MiMo 音频选型

用户目标：画面筛选不能使已有音频、已成功解码的画面全部作废；定义可解释、受控成本的选帧规则。先完成本地调整，再由用户统一手测。本轮不切换模型、不调用云端。

## 本轮实现

1. 保持本地每秒 10 次低分辨率扫描，不把扫描次数当成云模型请求次数。
2. 一般动态画面限制为最多每秒 1 个变化候选；明显局部变化允许最短 0.2 秒间隔；首尾与每 30 秒兜底帧继续参与选取。不固定裁掉字幕区。
3. 自适应模式下，单个像素轻微波动不触发候选。显著像素变化需最大差值至少 32/255、至少 0.4% 像素差值达到 16/255；全局/局部变化仍使用独立阈值。快速闪现、小字或微小数字变化可能在候选阶段漏掉，不能承诺零遗漏。
4. OCR 后完全相同像素可复用。近似去重还要求：去空白后文字完全相同且至少 20 字符、当前识别行置信度均至少 0.75、64×64 灰度平均差不超过 2.5%、差值至少 32 的像素不超过 1.5%。文字不同则保留；空文字/低置信度不据此去重。OCR 本身认错的相同文本仍有误合并风险。
5. 本地候选最多 480，最终原图最多 240。到达上限后按相邻时间段合并代表帧，为后段留空间；记录缩减次数，不只保留视频开头。最终帧优先保留文字信息更丰富的代表。**这是预算内代表帧，不是完整逐页提取，也不是已实现的分批续扫。**
6. 解码/OCR 在中途失败时保留已成功结果。音频、可用画面继续进入各自提取阶段；总结带缺口。两路都没有可用输入才停止。
7. 新增「只转写音频」：对已保存的原媒体创建本地准备任务，完全跳过扫描/OCR；随后仍由用户确认云模型提取。新增「重新准备画面」用于旧失败输入。只处理当前这一条，不重同步收藏夹。
8. 完整准备仍是本地先音频、后画面，**尚不是音频云请求与画面扫描并行执行**。用户可选择音频单独路径，不必等画面。原视频保留。
9. 修复大量候选导致 FFmpeg 选择表达式递归过深：改用平衡表达式树。480 个候选的本机解码器表达式验证通过。
10. 解码器计时排除本地 OCR 消费回调耗时，避免将正常的 OCR 等待误报为解码超时；含本地消费的整轮仍有 600 秒边界，到界保留已有结果。此处不是云模型超时配置。
11. 手动本地重准备的当前输入不自动进入付费队列，即使启用了新增资料自动提取，也要在本次弹窗再次确认。

## 手动验收

- 旧 `frame_limit` 资料：打开提取 → 重新准备画面 → 本地准备完成后检查音频/画面数量 → 再决定是否确认模型提取。
- 只要讲话：提取 → 只转写音频 → 检查「音频 N 段、画面 0 张」→ 确认提取；结果应明确画面未提取。
- 单条失败不能清掉原文件和已成功正文；已有排队/运行任务不能重复提交媒体准备。
- 代表帧缩减或局部失败必须显示覆盖缺口，不标成逐页完整。
- 界面不会自动重跑旧失败任务。本次单元测试与本地原视频验证均不调用模型。

## MiMo Token Plan：截至 2026-10-06 的官方依据

官方 [套餐模型](https://mimo.mi.com/docs/zh-CN/quick-start/faq/token-plan/Plans&Pricing) 包含 `mimo-v2.6-flash` 与 `mimo-v2.5-asr`；共享套餐额度，并非独立免费配额。

[额度规则](https://mimo.mi.com/docs/zh-CN/quick-start/faq/token-plan/Usage&Quota)：Flash 未缓存输入每 token 100 Credits、输出每 token 200 Credits；ASR 每小时音频 30,000,000 Credits。以下按正常时段、无缓存估算，不是实测账单。

[Flash 音频理解](https://mimo.mi.com/docs/zh-CN/quick-start/usage-guide/multimodal-understanding/audio-understanding)：约每秒 6.25 音频 tokens。

| 比较项 | Flash | ASR |
|---|---|---|
| 1 小时纯音频输入 | 22,500 tokens，2.25M Credits | 30M Credits |
| 假设该小时输出 20,000 tokens | 加 4M，共约 6.25M Credits | 按时长仍为 30M Credits |
| 额外因素 | 文本提示、输出和思考 tokens、音频片段重叠另计 | 片段重叠会增加计费时长 |

此示例下 Flash 约用 ASR 的 21% 额度。不能把纯音频输入的 13.3 倍差直接称为总价差；实际以供应商 usage 和套餐扣额为准。总结的共同成本未计入，两种方案都需总结。

建议保留 Flash 为默认；ASR 作为纯逐字稿质量候选，不因名字含 ASR 就判断更便宜或更准。官方列出方言、嘈杂语音、歌词等识别能力，但本项目尚未做同音频 A/B 识别率对比，不能宣称 ASR 质量胜出。

## ASR 接入注意（本轮未切换）

[官方 ASR 接口](https://mimo.mi.com/docs/zh-CN/quick-start/usage-guide/audio/Speech-Recognition) 使用 `chat.completions` 的 `input_audio`，配 `asr_options.language`，不是直接把通用 `/audio/transcriptions` 换个模型名。样例仅传音频，不套用 Flash 的综合理解提示。

支持 wav/mp3，Base64 后不超过 10 MB。当前 240 秒、16kHz、单声道 16-bit WAV 约 7.68 MB，Base64 约 10.24 MB，处于或超过文档限制；若试 ASR，建议缩短至 180 秒或压缩 MP3，并验证 New API 转发格式。套餐支持不等于当前网关已做真实 ASR 调用验证。

后续如用户同意，选择普通话教程/中英术语/有背景音乐各一段，用同一份音频比较漏词、专名、数字、延迟和实际扣额；不自动双跑所有收藏。
