## 实际风险与未通过项目

补充完整问答测试：使用 builtin-quick-answer 和已配置的 mimo-v2.5，针对本测试库提出四问（品牌维度、当前计划、任务状态、资料未提供的预算）。SSE 读取等待 90 秒超时；随后通过官方消息接口查到用户消息已保存，assistant content 为空、is_completed=false、引用为空。因此本轮完整 RAG 问答未通过，不能根据摘要生成成功推断完整问答流程可用。尚未定位到模型供应商或应用管道的具体阻塞点。只针对该隔离会话请求停止，不重启服务、不修改模型配置。

测试脚本最初按流结束读取，后续加入 done 事件退出；但消息接口的空正文与未完成状态独立证明此次并非仅由客户端等待 EOF 导致“实际已回答但没显示”。实际回答质量、引用和未知问题拒答仍待验证。

后续停止接口按文档携带 message_id 后返回 success=true、Generation stopped；这是服务接受停止请求的凭证，未做 worker 清退的独立验证。

### 1. 首次处理的 seq_id 冲突

本轮 API 顺序快速提交，Lite 后台异步处理可重叠；其中一份文档在创建 chunks 时唯一键冲突。不能说是用户主动并行提交，也不能由此断言 SQLite 本身不可用。
源码 internal/application/repository/chunk.go 的 CreateChunks 会先调用 AssignChunkSeqIDs，再 CreateInBatches；internal/types/chunk.go 使用 MAX(seq_id)+1 分配编号。该“读最大值—插入”路径与观测到的竞争风险一致，但没有做受控并发复现或修复验证，根因判断仍是代码支持的推断。
生产接入门槛：小批量/单任务处理和失败状态检查作为临时措施；正式批量同步前需修复或验证该分配路径，不能把一次重试成功当作问题消失。

### 2. 文档摘要不是任务状态

tasks/job-001.json 原文完整且可检索，但其自动摘要是“No textual content was extractable from this document.”。
这证明原始内容保留与模型衍生摘要的质量应分别验收。查询真实任务状态应走结构化任务接口，不让 LLM 摘要决定完成与否。
同理，新版排第一只是本轮相关度表现，不是“自动识别当前有效版本”的保证。正式接入应先由版本/状态映射选择文档 ID，再调用限定范围检索。

## 与 OpenViking 上轮的对照

- 两者均完成小文本存取与语义定位。
- WeKnora 本轮提供稳定知识 ID、处理状态、错误信息、重新解析、分类移动和原文下载，适合文档管理模块。
- OpenViking 上轮云端连接曾在等待索引时超时但实际已更新，且当前版本查询中旧文档排名更高；不能将此推广为所有自托管部署结论。
- WeKnora 本轮正确文档均排前，但出现真实处理失败，因此不能只按检索排名宣布整体可靠性胜出。
- 尚未完成：20–30 份真实规模样本、PDF/图片/真实附件、删除恢复、进程重启恢复、权限隔离和 Wiki 历史回滚。版本号递增不等于已验证普通文档历史回滚。

## 阶段建议

文档管理优先继续采用已部署的 WeKnora 做候选，暂不为同一文档库再维护 OpenViking 副本；现有记忆机制不在本次迁移范围。
自己的内容模块继续管理素材、任务、审核与产物关联，通过统一 MCP 入口暴露；不把业务表插进 WeKnora 的内部数据库。
保留本地 Markdown/附件作为原件，初期做单向、可检查的同步。先修复或限制批处理风险，再做 20–30 份样本验收，之后才决定整库接入。
